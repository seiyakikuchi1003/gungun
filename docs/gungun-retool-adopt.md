# Re tool ブループリント → ぐんぐん取り込み方針（Claude Code用）

> Re tool（レンタルアプリ）の設計ブループリントから、ぐんぐんに取り入れるべき部分を選別。
> **大前提：Re toolはレンタル（返却あり・1対1）、ぐんぐんは物々交換（返却なし・玉突きの輪）。**
> 取引フローの根幹は違うので、状態機械・証拠写真の「返却」系はそのまま持ち込まない。
> 仕様の正はあくまで `docs/gungun-requirements.md`。Re toolは「良い実装パターンの参考」として使う。

---

## 0. 取り込みの3分類

| 分類 | 内容 | 扱い |
|---|---|---|
| ★そのまま取り込む | 設計・実装パターンとして優秀で、交換モデルでも有効 | 積極採用 |
| △一部だけ取り込む | 考え方は使えるが、交換モデル用に作り替える | 参考にして改変 |
| ✕取り込まない | レンタル固有（返却・日程・泊数） | 無視 |

---

## 1. ★そのまま取り込むべきもの（優先）

### 1-1. 状態遷移はすべて RPC（SECURITY DEFINER）経由にする
- テーブルに UPDATE ポリシーを与えず、**ステータス遷移は RPC がガード**（呼び出し者・現在ステータス・必須条件を検証）してから実行。
- クライアントが勝手に `status` を書き換えられない設計。
- **ぐんぐんの収穫・発送・受け取り・評価も、すべてこの方式にする。**
- 全RPCは `SECURITY DEFINER` + `search_path=''`（`public.`明示）、`revoke execute from public,anon; grant to authenticated;`
> これは今の水やり・収穫修正の方針と完全に一致。より厳密にする。

### 1-2. 機密情報のテーブル分離
- `profiles`（公開：表示名・アバター・bio・評価）
- `user_private_info`（機密：住所・電話）→ **本人のみ RLS**
- 住所・電話を profiles に混ぜない。**発送に使う住所は機密テーブルへ分離。**
> ぐんぐんも発送で住所を扱うので、この分離をそのまま採用。

### 1-3. 金額はサーバー側スナップショットを信頼
- 取引作成時に商品の価格・名称を取引テーブルにコピー。
- 決済額はDBの値を使い、**クライアント送信値は信用しない**。
> ぐんぐんの肥料消費・プレミアム決済でも、金額はサーバー側の値を使う。

### 1-4. Stripe決済の作り（Edge Function 方式）
- `STRIPE_SECRET_KEY` は **Edge Function の環境シークレットのみ**（アプリに出さない）。
- Edge Function `create-payment-intent` で、実行者・ステータス・金額を検証してから PaymentIntent を作る。
- アプリは `initPaymentSheet`（Apple/Google Pay 試行→カード）→ `presentPaymentSheet`。
- 成功後に RPC を呼んでステータス遷移。
> ぐんぐんの肥料チャージ・プレミアムも、この「Edge Functionでキーを隠す」形にする。

### 1-5. 取引詳細画面の作り（ActionCard 方式）★項目10の答え
- **取引詳細画面（`transaction/[id]`）を最重要ファイルとして作る。**
- **ステッパー**で進捗を可視化（ぐんぐんは 収穫→発送→受取→評価→完了）。
- **ActionCard**：ステータス×役割（送る人/受け取る人）に応じて「次にやるべき操作＋ボタン」を1枚のカードで表示。
  - 色分け：brand（自分の番）/ pending（相手待ち）/ done（完了）。
- ステータスのラベル・色を1ファイルに定義（`transactionLabels` 相当）。
> **8/12で保留にした「取引詳細（項目10）」は、この ActionCard 方式で作る。**
> 「誰と取引しているか・今どの段階か・次に何を押すか」が1画面でわかる。

### 1-6. 取引チャット（Realtime）
- 取引参加者のみ送受信、Supabase Realtime で即時配信。
- 取引詳細から取引メッセージに行ける。
> ぐんぐんの取引メッセージもこの形（既に要件にあるが、Realtimeで即時反映を徹底）。

### 1-7. 通知はトリガで自動生成
- `notify_transaction_change()`：取引の作成・全遷移で相手に通知。
- `notify_new_message()`：新着メッセージで相手に通知。
- 各遷移の通知先・文言を1つのマイグレーションに表で定義。
- プッシュのルーティング：message→取引メッセージ / transaction→取引詳細 / product→商品 …
> ぐんぐんの「通知タップで該当ページ遷移」を、この方式で実装。

### 1-8. メール打ち間違い検出（認証）
- 登録時、メールアドレスのタイプミスを Levenshtein 距離で検出して修正提案。
- 届かない時のフォールバック（再送・スパム案内・アドレス編集）。
> ぐんぐんの新規登録でも採用すると離脱が減る。

### 1-9. 論理削除（deleted_at）を基本にする
- 削除は物理削除でなく `deleted_at` で論理削除。
> データ移行・運営対応で安全。ぐんぐんでも採用。

### 1-10. 管理画面のアーキテクチャ
- `is_admin()` RPC でガード、全管理RPCに is_admin チェック。
- 汎用CRUD（`data/[table]`）・CSVエクスポート・通報対応・お知らせ配信・ポップアップ・バナー。
- `app_documents`（規約・会社概要・問い合わせ先）を**管理画面から編集**。
> ぐんぐんの管理画面は、この構成をほぼそのまま採用してよい。特に「規約を管理画面から差し替え可能に」は既出要件と一致。

## 2. △一部だけ取り込む（交換モデル用に作り替え）

### 2-1. 取引の状態機械 → ぐんぐん用に置き換え
- Re tool：`requested→approved→paid→shipped→in_use→returning→return_check→completed`（返却あり）
- **ぐんぐん**：収穫で輪ができた後、各人が
  `trading（発送待ち）→ shipped（発送済み）→ received（受取済み）→ 双方評価 → completed`
  - **申請・承認・決済（paid）は無し**（交換なので金銭のやり取りが取引単位では発生しない）
  - **返却系（in_use / returning / return_check）は無し**
  - 「発送しないと受け取れない」制約は維持。
> 状態機械の"作り方"（RPCでガード）は真似るが、"段階"はぐんぐん用にする。

### 2-2. 証拠写真 → 簡略版（任意）
- Re tool：pre_ship / receipt / pre_return の3段階必須。
- **ぐんぐん**：まずは**任意**。入れるなら「発送前」「受領時」の2段階に留める。返却系は無し。
> v1では必須にしない。トラブル対策として将来検討。

### 2-3. レビュー → ぐんぐんの2軸に
- Re tool：1取引1人1回、profiles集計、借主/貸主で設問が違う。
- **ぐんぐん**：送った側=やり取りの円滑さ、受け取った側=商品の質。輪の全員が対象。
  - `UNIQUE(transaction, reviewer)` の1回制約、トリガでの profiles 評価集計は**そのまま採用**。
> 集計の仕組みは真似る。設問はぐんぐんの2軸。

### 2-4. 配送・追跡 → そのまま使える
- 配送業者の追跡URL自動生成（ヤマト/日本郵便/佐川）。追跡番号を保存し、取引詳細でリンク生成。
- ぐんぐんは「発送する側が送料負担・配送」なので、この配送・追跡はほぼそのまま使える。
- 手渡しは基本不要（配送のみでよい）。

### 2-5. デザインシステム → トークンの考え方を採用（色はぐんぐんのまま）
- theme.ts と tailwind.config.js を同期／マジックナンバー禁止／4pxグリッド／角丸 sm4-md8-lg12。
- **ただし色はぐんぐんのブランド（緑×オレンジ×クリーム）を使う。** Re toolの青（accent）は使わない。
- ステータスバッジの作り（背景=色+26%透明 + 太字テキスト）は流用可。

## 3. ✕ 取り込まないもの（レンタル固有）

- 日程カレンダー・期間選択・泊数（`rental_nights`）
- 空き検索（`search_available_products`）
- 返却フェーズ全般（returning / return_check / 返却状態評価）
- 返却延滞計算
- プラットフォーム手数料15%・振込・売上確定・出金（※ぐんぐんはユーザー間で金銭が動かないため不要。**プレミアム/肥料課金はぐんぐん独自の別ロジック**）

> ぐんぐんは「モノとモノの交換」で、取引ごとに金銭が動かない。
> Re toolの「決済・手数料・振込・返却」まわりは、ぐんぐんの取引には**持ち込まない**。

## 4. いま優先して取り込むべき順（実務）

```
1. 取引詳細画面（ActionCard＋ステッパー）★8/12の項目10の答え。最優先
2. 状態遷移をRPCでガードする方式に統一（収穫・発送・受取・評価）
3. 通知のトリガ自動生成＋プッシュのルーティング
4. 機密情報（住所・電話）のテーブル分離
5. 配送業者の追跡URL自動生成
6. 管理画面アーキテクチャ（is_admin・汎用CRUD・app_documents）
7. メール打ち間違い検出／論理削除／レビュー集計トリガ
```

## 5. Claude Codeへの投げ方（例）

```
docs/gungun-retool-adopt.md を読んでください。
これは参考にするレンタルアプリの設計を、ぐんぐん（物々交換）向けに取捨選択したものです。

まず「1-5 取引詳細画面（ActionCard方式）」を実装してください。
ぐんぐんの取引段階（収穫→発送→受取→評価→完了）に合わせたステッパーと、
ステータス×役割で「次にやる操作」を出す ActionCard を作ってください。

レンタル固有（返却・日程・泊数・手数料・振込）は取り込まないでください。
仕様の正は docs/gungun-requirements.md です。
```

---

## 6. ひとことで

**Re toolからは「作り方（RPCガード・機密分離・取引詳細のActionCard・通知トリガ・管理画面）」を借り、
「レンタルの中身（返却・日程・手数料・振込）」は捨てる。**
特に、8/12で保留した**取引詳細画面は、Re toolのActionCard方式がそのまま答え**になる。
